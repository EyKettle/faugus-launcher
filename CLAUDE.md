# Faugus Launcher — notes for Claude

GTK4/PyGObject game launcher (Python). Main window logic lives in `faugus/launcher.py` (large file).

## Standing rules

- **No code comments, anywhere in this codebase.** Not even to explain non-obvious WHY (e.g. import ordering). This has been confirmed repeatedly — do not add any.
- **Keyboard and gamepad navigation on the main screen must be identical and standardized.** Any fix to one input method must be mirrored in the other, or better, implemented once in shared code both paths call.
- Left/Right must never let focus escape the games grid to another widget area. Only Up/Down may escape (Up only escapes to the top bar in List mode, and only if a top bar exists).
- Don't reimplement GTK's native focus/keynav with custom geometric logic when a real GTK bug/quirk is the actual root cause — find the root cause instead (see Testing below).

## Banner background rendering — two-layer (image + isolated gradient), no PIL

**Note:** `CLAUDE.md` is gitignored, so nothing below survives a session unless it's also true of the committed code. A prior session documented a `Gtk.Picture`-based two-layer fix here, but it was never actually committed — `git log -S` on every string this doc claimed (`banner-fade-box`, `Gtk.Picture` in the banner path) found zero hits, and the live code was still the single-combined-declaration version. Treat this section as accurate only as of the commit that introduces the CSS classes it names below (`banner-bg-fade-N`, `launcher-screen-banner-fade`) — verify with `grep` before trusting it if this note is gone.

Under KDE Plasma fractional scaling (e.g. 125%) the Covers/Carrousel background banner (and the install-screen static banner, same underlying pattern) showed a ~1px strip of un-faded banner image at the very bottom edge — the gradient's 100% (fully-opaque) stop was landing one device-pixel short of the box's true bottom row under fractional scaling, so that last row of raw image showed through unfaded. Earlier diagnostic history (a different, narrower seam symptom — a bright edge line, not a 1px unfaded strip) all kept the gradient and image **combined in one CSS `background-image` declaration** (`linear-gradient(...), url(...)`) and is preserved for context in git history of this file; none of those fixed the eventual real symptom, and a PIL-precompositing attempt was reverted for memory/speed regressions (~10MB RSS import tax + per-switch composite cost) — avoid re-reaching for PIL here.

**Current fix** (per user-supplied approach, from a working Gemini-authored GTK4 test snippet, confirmed by the user against real KDE 125% hardware): split the image and the gradient into two separate stacked `Gtk.Box` overlay children instead of one combined CSS declaration, both sized identically every frame from the existing tick callback (`height = int(width / banner_ratio)`, no `+Npx` fudge on the size request):
- `banner-bg-image-{i}` / `launcher-screen-banner-image`: `background-image: url(...)` only, `background-size: 100% 100%`.
- `banner-bg-fade-{i}` / `launcher-screen-banner-fade` (stacked on top, `set_can_target(False)`): `background-image: linear-gradient(to bottom, transparent 0%, rgb(fade) 100%)` (plain two-stop gradient, unchanged from before this bug) **plus** `transform: scaleY(1.015); transform-origin: top;`. `transform` is a paint-time-only CSS property — it doesn't affect layout/allocation — so this stretches the gradient's *rendered* content 1.5% taller than the box while the box's own allocated size (and everything else's layout) stays exactly as it was. The stretch pushes the gradient's 100%-opaque stop physically past the box's bottom edge, so whatever row the fractional-scale renderer's device-pixel rounding lands on is guaranteed to already be inside the overscaled solid region.
- A same-shaped fix built instead from CSS `calc(100% - 2px)` gradient stops (no `transform`, forcing only the last ~2px of the *unscaled* gradient solid) was tried first and looked identical in Xvfb, but **did not fix the seam on real KDE 125% hardware** — reverted. Don't re-try that path; the `transform: scaleY` on the fade box is the confirmed-working mechanism, not a placeholder for something simpler.
- Both boxes stay plain `Gtk.Box` + CSS (not `Gtk.Picture`) — the install-screen path (`update_launcher_banner_css`) still needs the `_banner_css_cache_counter`/`shutil.copyfile` cache-busting hack for its image layer, because that path's live Add/Edit-Game banner preview reuses the same file path across edits and GTK's CSS `url()` loader caches by URI string. The main-screen path (`update_background`) doesn't need it — each game's banner URI already differs.

History: the `scaleY(1.015)` version was implemented, then briefly swapped for the `calc(100% - 2px)` variant in the same session, then swapped back after the user reported the line reappeared on their real KDE 125% desktop — i.e. `calc()` was the one that failed real-hardware testing, `scaleY` is the one to keep. Re-verify against real KDE 125% hardware after any future edit to this code before assuming it still works; Xvfb here only ever runs at 100% scale (X11, no fractional scaling) so it can catch layout regressions but not re-confirm the actual fix.

## Data/UI sync gotcha

Any code that mutates a game's in-memory state (category, etc.) after startup must update the `Game` objects in `self.games` directly (`next(g for g in self.games if g.gameid == id)`), not by looping `widget_children(self.flowbox)` — that loop finds nothing in carrousel mode since `load_games()` skips populating `self.flowbox` there, silently leaving `self.games` stale. After mutating, refresh the visible mode explicitly: `self.flowbox.invalidate_filter()` for flowbox modes, `self.render_carrousel()` for carrousel (see `on_category_menu_item_selected` for the canonical carrousel-aware branch). This bit `on_context_menu_category`, `_update_games_category`, and `_remove_games_category` all at once — check for this pattern before adding new game-mutation code paths.

## Navigation architecture

- `faugus/main_screen_nav.py` is the shared, **Manette-free** navigation module. Both `faugus/launcher.py` (keyboard, `Gtk.EventControllerKey`) and `faugus/gamepad.py` (gamepad, via Manette) call into it so keyboard/gamepad behavior can't drift apart. `faugus/gamepad.py` must only be imported lazily/conditionally (`if self.gamepad_navigation: import faugus.gamepad as gamepad`) since it hard-depends on the `Manette` GI binding — never import it unconditionally at module level from `launcher.py`.
- `Gtk.FlowBox` does not sync its internal keynav cursor on a programmatic `grab_focus()`. Use `focus_flowbox_child(flowbox, child)` in `main_screen_nav.py` (grab + select + a `child_focus` TAB_FORWARD/BACKWARD nudge) whenever code needs to move focus onto a flowbox child — a plain `grab_focus()` leaves keynav desynced until a real click happens.
- `Gtk.Entry.set_focusable(False)` on the wrapper is a no-op; the real focusable widget is `entry.get_delegate()`. Used for the search-box-styled decorative entries inside game cards.

## Interface Mode vs SteamGridDB (art source)

`interface-mode` is a pure layout choice: **List, Grid, Covers, Carrousel** — SteamGridDB is *not* one of its values. Whether artwork comes from the SteamGridDB API is an orthogonal `steamgriddb-enabled` checkbox (paired with the existing API-key link+entry in Settings), gated together with a non-empty `steamgriddb-api-key` (see `AddGame.__init__`'s `self.steamgriddb_enabled` and the equivalent local computation in `on_combobox_changed`). Rule of thumb when touching `interface_mode`-conditioned code:
- **Layout/"does cover art apply here" sites** (dominant-color source, flowbox cover-container styling, save-game cover/banner-file persistence, cover column visibility) key off `interface_mode in ("Covers", "Carrousel")`.
- **"Where does the art actually come from" sites** (icon-extraction-from-exe skip, SteamGridDB suggestion popover, the `fetch_icon`/`fetch_banner_art` flags in `get_artwork()`, the AddGame banner block, the SteamGridDB-picker-vs-native-file-chooser branch on cover/banner/icon click) key off `steamgriddb_enabled` instead — icon sourcing applies to *all* interface modes now (List/Grid included), not just Covers/Carrousel.
- Unchecked + Covers/Carrousel still gets a cover, via the free keyless Bottles fallback (`steamgrid.usebottles.com`, wired into `AddGame.get_artwork`'s `fetch_artwork` worker) — this is real, already-working, not something to rebuild.
- `carrousel_active()` is just `self.interface_mode == "Carrousel"` — no separate enabled flag to check.

## Carrousel mode

Custom horizontal carousel (`interface-mode == "Carrousel"`), built on a `Gtk.Fixed` (`self.carrousel_fixed`), **not** a real `Gtk.FlowBox`. Key facts:

- Fixed pool of 9 physical "slot" widgets spanning offsets `-4..4` (`carrousel_min_offset`/`carrousel_max_offset`), recycled to show different games as the carousel scrolls — offset is a position relative to the centered/selected game, not a game identity. `carrousel_visible_games()` returns the current sorted/filtered game list; `carrousel_index` is the index of the selected game within it.
- `carrousel_move(delta)` handles both single-step nav (delta=±1) and large jumps (clicking a distant slot, or a coalesced multi-press). Offset wraparound uses full modular arithmetic across the whole span — a naive "clamp to the opposite boundary" only works for `abs(delta)==1` and corrupts multiple slots (duplicate offsets, gaps) for larger jumps.
- Slots that need to recycle to a new game (their raw target offset falls outside `[min,max]`) are pinned invisible at the boundary edge for the whole animation and only revealed (repositioned + made visible) in one shot when the tick-animation completes (`_settle_offset` mechanism). Interpolating their position directly overlaps/tears against other slots that are mid-slide — don't do that.
- If a new `carrousel_move` interrupts an in-flight animation, flush the in-flight one first (settle every slot to its true logical `offset`, cancel the tick callback) before computing the new move — otherwise visual and logical offset desync across rapid repeated input.
- Rapid repeated single-step moves (holding an arrow key / gamepad direction) are coalesced in `main_screen_nav.py` (`carrousel_move_coalesced`) into fewer, larger animated jumps instead of interrupting-and-restarting on every repeat event — a single tap still moves instantly.
- Selection highlight (glow/scale) is driven entirely by Python-computed inline CSS per slot (`layout_carrousel_slot`), not GTK `:selected` state (these aren't real selectable children). It dims to ~50% when `carrousel_fixed` doesn't have literal keyboard focus, full when it does — this mirrors the non-carrousel modes' `:selected` vs `:selected:focus` CSS split, so keep both in sync if either changes.
- Custom sort ("Sort" = Custom) drag-to-reorder is implemented with real `Gtk.DragSource`/`Gtk.DropTarget` per slot (mirrors the flowbox drag implementation, same `custom_order_data` dict + `CUSTOM_ORDER` json file), throttled to at most one reorder per 500ms during the drag with an immediate flush on drop.
- Mouse wheel scroll (`on_carrousel_scroll`, a `Gtk.EventControllerScroll` on `carrousel_fixed`) steps the carousel one game per notch, same as arrow keys — regrabs focus and reuses `carrousel_move_coalesced` so rapid/trackpad scroll events coalesce instead of stuttering.

## Testing methodology

- **Never open test/GUI windows on the real display.** Always test in an isolated `Xvfb` (`Xvfb :99 -screen 0 1280x800x24`) with `DISPLAY=:99 GDK_BACKEND=x11`.
- Isolate config/data too: set `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`XDG_STATE_HOME` to a scratch dir *before* importing `faugus.path_manager` (paths are computed at import time), and monkey-patch `faugus.path_manager.APP_ID`/`TRAY_BUS_NAME` to a `.test` suffix so the test instance doesn't collide with the user's real running app over D-Bus. Copy `games.json`/`covers` from the real `~/.local/share/faugus-launcher/` into the scratch dir (read-only reference data) rather than fabricating fake games — never write into the real one.
- Drive the app with `xdotool` (`mousemove`/`click`, `key --clearmodifiers`, `mousedown`/`mousemove`/`mouseup` for drags) and capture state with `PIL.ImageGrab` (`DISPLAY=:99` env) rather than guessing from reading code — this session's bugs repeatedly turned out different from the first hypothesis.
- Verify claims empirically before reporting a fix as done. Don't guess.
- **The `APP_ID` monkey-patch does not survive `os.execv`.** Several settings-save paths (`interface-mode`, `theme-engine`, `background-mode`, etc. changing) call `os.execv(sys.executable, ['-m', 'faugus.launcher'], ...)` to restart the process — this *replaces* the process image with a fresh, un-patched import of `faugus.launcher`, so it re-registers the **real** D-Bus app id and can signal/activate the user's real running instance even though the test process's env vars (XDG_*) are inherited and stay isolated. Before exercising any settings flow that might trigger a restart, monkey-patch `os.execv` itself to a no-op/logging stub in the test wrapper (`os.execv = lambda *a, **k: print(f"execv suppressed: {a}")`) — the settings dialog's own `update_config_file()` call already persists to the (isolated) config file before the `execv` checks run, so the no-op doesn't lose the setting; just relaunch the test process fresh afterward to pick up the new config.
